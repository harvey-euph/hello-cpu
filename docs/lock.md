# x86-64 LOCK 前綴與原子指令全解：從硬體匯流排鎖、快取行鎖到 MFENCE 終極對決

在多核心處理器與現代併發系統中，**`LOCK` 前綴（機器碼 `0xF0`）** 是支撐整個作業系統、資料庫與高階語言原子型別（如 C++ `std::atomic`、Java `Atomic*`、Rust `Arc`）的底層核心支柱。

然而，圍繞著 `LOCK` 前綴，始終存在著許多令人困惑的底層疑問：
* 為什麼隨便加 `LOCK` 會導致 CPU 當場拋出 `#UD` 異常崩潰？
* 為什麼明明有 `MFENCE` 指令，編譯器和 JVM 卻經常「掛羊頭賣狗肉」，用 `lock or [rsp], 0` 來當記憶體屏障？
* 做那麼多事（讀取、ALU 運算、寫回、改旗標）的 `LOCK` 指令，**怎麼可能在某些 CPU 上比純粹屏障的 `MFENCE` 還要快？**

本文將深入 x86-64 微架構矽晶片電路，全面剖析 `LOCK` 前綴的運作原理、合法白名單、自帶鎖定的特權指令，以及它與 `MFENCE` 之間的世紀對決。

## 一、什麼是 `LOCK` 前綴？（RMW 原子性本質）

在單核心時代，執行一行 `add [counter], 1` 似乎是理所當然的原子操作。但在微架構內部，它其實包含了三個不可分割的子步驟——**RMW（Read-Modify-Write，讀取 - 修改 - 寫回）**：

1. **Read**：從 L1/L2 快取或記憶體讀取 `counter` 的目前數值到 CPU 內部的暫存器。
2. **Modify**：ALU 執行加 1 運算。
3. **Write**：將新數值寫回快取或記憶體。

### 多核心競態條件（Race Condition）
在多核心處理器中，若核心 A 與核心 B 同時執行 `add [counter], 1`：
* 核心 A 讀到舊值 `10`。
* 核心 B 也同時讀到舊值 `10`。
* 核心 A 算完寫回 `11`；核心 B 也算完寫回 `11`。
* **致命後果**：兩次加法操作，最終計數器只增加了 1（遺失更新，Lost Update）。

加上 **`LOCK` 前綴（`lock add [counter], 1`）** 後，CPU 硬體會保證這整個「讀取 $\to$ 修改 $\to$ 寫回」過程具備**不可分割的原子性（Atomicity）**，任何其他核心在此期間都無法插隊讀寫該記憶體。

## 二、嚴格的硬體白名單：不是想加就能加！

很多初學者誤以為 `LOCK` 前綴可以隨意套用在任何指令前（例如幻想著寫 `lock mov [ptr], rax`）。

> [!CAUTION]
> **硬體報警鐵律（Invalid Opcode Exception, #UD）**：  
> Intel 與 AMD 官方手冊明確規範：**`LOCK` 前綴只支援特定白名單指令，且目的運算元必須是記憶體（`[mem]`）！**  
> * 若將 `LOCK` 放在目標為暫存器的指令前（如 `lock add eax, 1`）；
> * 或放在不在白名單中的指令前（如 `lock mov [ptr], 1`、`lock test [ptr], 1`）；  
> CPU 解碼器會在解碼階段**直接拋出 `#UD`（無效操作碼中斷）**，作業系統會直接向行程發送 `SIGILL` 終止程式！

### Intel 官方規範之合法指令清單：

| 指令分類 | 支援 `LOCK` 的指令 | 典型編譯器與併發用途 |
| :--- | :--- | :--- |
| **算術運算** | **`ADD`**, **`ADC`**, **`SUB`**, **`SBB`**, **`NEG`**, **`INC`**, **`DEC`** | 原子計數器（`atomic++` / `atomic--`）、自旋鎖票號 |
| **邏輯運算** | **`AND`**, **`OR`**, **`XOR`**, **`NOT`** | 原子位元遮罩修改、標記狀態清除 |
| **位元測試修改**| **`BTS`**, **`BTR`**, **`BTC`** | 點陣圖（Bitmap）分配器、位元鎖（Bitlock）搶鎖 |
| **交換與加法** | **`XADD`**（Exchange and Add） | **原子 Fetch-and-Add**（C++ `fetch_add`、引用計數核心） |
| **比較並交換** | **`CMPXCHG`**, **`CMPXCHG8B`**, **`CMPXCHG16B`** | **CAS（Compare-And-Swap）**、所有無鎖資料結構的核心 |

## 三、天生自帶 LOCK 的特權階級：`XCHG` 指令

在 x86 指令集中，有一個極為罕見的特權指令——**`XCHG`（原子交換）**：

```assembly
xchg [mutex_flag], eax    # 注意看：完全沒有寫 lock 前綴！
```

* **Intel 手冊明文鐵律**：  
  只要 `XCHG` 指令的運算元牽涉到**記憶體（`[mem]`）**，無論程式設計師有沒有手動加上 `0xF0`（LOCK 前綴），**CPU 硬體一律自動、強制施加 LOCK 鎖定協定！**
* 它在硬體層級永遠不可分割，因此是實作自旋鎖（Spinlock）`try_lock` 最經典的原語。

## 四、微架構演進：從「物理匯流排鎖」到「MESI 快取行鎖」

CPU 究竟是怎麼在硬體層次「鎖住」記憶體的？這在晶片製造史上經歷了一場巨大的微架構革命：

### 1. 舊時代（8086 ~ Pentium）：粗暴的「物理匯流排鎖（Bus Lock）」
* 在早期的多處理器架構中，當 CPU 解碼器看到 `LOCK` 前綴時，它會直接在晶片腳位上拉低 **`#LOCK` 物理訊號線**。
* **災難性後果**：整條實體主機板記憶體匯流排被強行凍結！**所有其他 CPU 核心、DMA 網路卡、磁碟控制器全數被迫停機等待**，直到該指令執行完畢。這種鎖定方式延遲極高，嚴重傷害系統吞吐量。

### 2. 現代架構（Pentium Pro 至今）：優雅的「快取行鎖（Cache Lock）」
現代 Intel Core / Xeon 與 AMD Ryzen / EPYC 處理器全面採用 **MESI / MOESI 快取一致性協定** 實現快取行鎖定：
* **快取命中（Cache Line Hit）**：  
  若目標變數已經存在於當前核心的 **L1 Data Cache** 中，且**沒有跨越 64-Byte 快取行邊界**：
  * CPU **根本不會去動實體匯流排**！
  * 核心透過內部快取互聯網格，直接取得該快取行的 **Modified (M) 獨佔狀態**，並在此期間攔截並延後其他核心發出的讀寫嗅探請求（Snoop Probes）。
  * 整個原子 RMW 操作在 L1 快取內部以 **10 ~ 20 個時脈週期** 極速完成！

### 3. 跨快取行存取：核彈級災難「Split Lock」
如果變數沒有自然對齊，剛好橫跨了兩個 64-Byte 快取行的分界線（例如位址落在 `0x3F`）：
* CPU 的快取控制器無法用單一快取行鎖定保證跨行原子性。
* **退化處罰**：CPU 被迫倒退回最原始、最殘暴的 **Bus Lock（匯流排鎖）**！整台伺服器所有核心瞬間停頓數千個週期。
*(現代 Linux 核心甚至設置了 `/proc/sys/kernel/split_lock_mitigate` 機制，一旦偵測到程式觸發 Split Lock 會強制將其降速或以 SIGBUS 終止)*。

## 五、四大天王原子指令實戰解析

在現代高階語言底層，有 4 條帶 `LOCK` 的指令支撐了全世界絕大多數的併發程式庫：

### 1. `LOCK XADD`（原子加法並回傳舊值）
* **對應高階語法**：C++ `std::atomic::fetch_add`、Rust `fetch_add`。
* **核心地位**：智慧指標的引用計數管理——**`std::shared_ptr` 的複製與解構、Rust `Arc::clone()` / `drop()`**，底層 100% 依賴 `lock xadd`。
*(本專案已實作展示範例：[`src/demo/1989_xadd.s`](1989_xadd.s))*。

### 2. `LOCK CMPXCHG`（比較並交換，CAS）
* **對應高階語法**：C++ `compare_exchange_strong` / `weak`。
* **核心地位**：非阻塞無鎖資料結構（Lock-free Queue、Treiber Stack）的數學核心。檢查記憶體是否仍為預期值，若是則原子寫入新值，否則載回最新值重試。

### 3. `LOCK CMPXCHG16B`（128 位元雙倍 CAS）
* **核心地位**：徹底終結無鎖鏈結串列中的 **ABA 幽靈問題**。
* **運作機制**：同時原子比較與置換「**64 位元節點指標 + 64 位元版本計數器（Version Tag）**」。即便指標位址被記憶體配置器複用，只要版本號不同，CAS 就會安全拒絕寫入。
*(本專案已實作展示範例：[`src/demo/2004_cx16.s`](2004_cx16.s))*。

### 4. `LOCK BTS` / `LOCK BTR`（原子位元測試與翻轉）
* **核心地位**：高密度點陣圖（Bitmap）分配器、Linux 核心位元自旋鎖（Bitlock）。
* **運作機制**：原子地將某個位元設為 1（`BTS`）或 0（`BTR`），並將該位元的原值存入進位旗標 `CF`。若 `CF == 0` 代表搶鎖成功，若 `CF == 1` 代表已被他人持有。

## 六、深度對決：LOCK 真的比 MFENCE 更好嗎？

很多系統工程師在閱讀編譯器輸出時，常會驚訝地發現：  
當 C++ 要求產生完全順序一致性屏障（`seq_cst`）時，編譯器往往發射：
```assembly
# GCC / Clang 偏好的全屏障寫法：
mov [ptr], val
lock or dword ptr [rsp], 0   # 拿棧頂無關痛癢的位址做一次原子 OR 操作！
```
而不是教科書上的：
```assembly
mov [ptr], val
mfence
```

### 兩者在硬體上的全方位對照：

| 評估項目 | `lock or [rsp], 0` / `xchg` | `mfence` | 贏家與考量 |
| :--- | :---: | :---: | :--- |
| **舊架構延遲 (Haswell 前)** | **⚡ 約 18 ~ 22 週期** | 🐢 約 35 ~ 45 週期 | **LOCK 大勝**（快上一倍） |
| **現代架構延遲 (Skylake 後)**| ⚡ 約 15 ~ 18 週期 | ⚡ 約 15 ~ 20 週期 | **基本打平**（MFENCE 已微碼重構） |
| **EFLAGS 旗標影響** | ❌ **破壞 ZF, SF, PF, CF, OF** | **✅ 零副作用（完全不改旗標）** | **MFENCE 完勝** |
| **暫存器 / 堆疊干擾** | ❌ 需讀寫 `[rsp]` 或霸佔暫存器 | **✅ 零污染（純粹微架構管線屏障）**| **MFENCE 完勝** |
| **弱記憶體序 (WC / MOVNT)**| ❌ **無效！** 無法排空非暫態緩衝區 | **✅ 有效！** 強制排空所有記憶體類型 | **MFENCE 完勝** |
| **指令長度** | 5 位元組 (`f0 83 4c 24 00 00`) | **3 位元組 (`0f ae f0`)** | **MFENCE 較小** |

## 七、怎麼可能 LOCK 比 MFENCE 更快？微架構真相大揭秘

從純邏輯上看：
* `lock or [rsp], 0`：要讀記憶體、走 ALU 算 OR、寫回記憶體、更新旗標、鎖快取。
* `mfence`：什麼運算都沒做，不碰堆疊、不改旗標、不碰暫存器。

**做這麼多事的指令，怎麼可能比什麼都沒做的指令還要快？**

這背後是晶片工程設計中的三個殘酷現實：

### 1. 「親生兒子（硬體快線）」vs.「後媽生的（微碼氣泡）」
* **`LOCK` 是晶片的心臟**：Intel/AMD 投入了極其龐大的硬體電路，在 L1 Data Cache 控制器中直接焊死了專門的原子狀態機，全硬體管線零延遲切入。
* **早期的 `MFENCE` 走的是保守微碼**：在 Nehalem 到 Haswell 時代，`MFENCE` 甚至沒有專屬硬體快線，而是被寫在微碼（MSROM）中！它的實作極為粗暴——不僅等待 Store Buffer，**還會強行凍結指令分派器、清空指令重排序快取（ROB），在管線中製造一個巨大的空洞（Pipeline Bubble）**，光是這套微碼停頓就白白浪費了 30 多個週期！

### 2. `[rsp]` 棧頂的「零跨核心通訊開銷」偷吃步
為什麼大家做 LOCK 屏障時，都指定堆疊頂端 `[rsp]`？
* `[rsp]` 是當前執行緒的**私有堆疊**！
* 它 **100% 永遠常駐在當前核心的 L1 Data Cache 中**！
* 絕對不會有第二顆核心來搶你的 `[rsp]`，它的狀態永遠是 **Modified (M) 獨佔狀態**！
* **這意味著它根本不需要對外發送任何 MESI 匯流排探針**！整套原子操作完全是在本機私有的 L1 快取內自娛自樂，只要 **15 ~ 18 個週期** 就完成了。

### 3. 管轄邊界差異：只管 L1 快取 vs. 要管全域設備
* `lock or [rsp], 0` 只需要確保當前核心的 Store Buffer 刷入 L1 快取即可交差。
* `mfence` 則必須對**全系統所有記憶體類型負責**！它必須向系統代理（System Agent）與晶片內部網格發出確認，等待 Write-Combining (WC) 緩衝區以及外部 PCIe/MMIO 設備的所有掛起交易全部清空，代價自然沈重得多。

## 八、總結速查表

| 指令寫法 | 是否合法？ | 是否自帶全屏障？ | 微架構本質說明 |
| :--- | :---: | :---: | :--- |
| **`lock add [rdi], 1`** | **✅ 合法** | **✅ 是** | 原子遞增記憶體，觸發 Cache Lock 並排空 Store Buffer |
| `add [rdi], 1` | ✅ 合法 | ❌ 否 | 普通 RMW 操作，多執行緒同時執行會漏失更新 |
| **`xchg [rdi], rax`** | **✅ 合法** | **✅ 是** | **天生自帶隱式 LOCK**，不寫 `0xF0` 硬體也強制鎖定 |
| `lock add rax, 1` | ❌ **非法** | - | 目標是暫存器，硬體當場拋出 **`#UD` 崩潰** |
| `lock mov [rdi], 1` | ❌ **非法** | - | `MOV` 不在白名單內，硬體當場拋出 **`#UD` 崩潰** |
| **`mfence`** | **✅ 合法** | **✅ 是** | 純記憶體屏障，零旗標副作用，唯一能管轄 WC 弱記憶體序 |
